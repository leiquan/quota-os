Banner: Version: 015 (559daed). GICv2 found. Host clock, not icount.
Menu 1 ran and returned to select>. The same boot's "measured since boot"
kernel max was 80451 ticks against reserve 21875 (margin negative).
That line is host time. It is not an icount acceptance result and it
is not evidence of hardware isolation.

64M delivered image, same machine flags, did not reach select>:
  boot-64m-command.txt
  boot-64m-serial.raw
It printed the 64 MB memory line, cache colors (11 own colors, padding
3584 KB), then:
  [boot] ERROR: no GICv2 ... or GICv3 ...
  [boot] halted: no supported interrupt controller
dumpdtb of virt,gic-version=2 at 64M and 128M both contain
compatible = "arm,cortex-a15-gic". The halt is not "this QEMU has no
GIC". Developer analysis of the DTB header plus color_init's writes:
the in-guest DTB is about 7510 bytes of structure+strings inside a
header whose totalsize is 1048576. color_init runs after the memory
node is parsed and writes the first word of each Tier-1 page.
  64M DTB at 0x42000000: writes hit offsets 0 and 4096 (inside the
  struct). The GIC walk then fails.
  128M DTB at 0x44000000: the only hit is offset 0 (magic). The walk
  does not re-check the magic, so GICv2 still comes up.
This 64M halt is a baseline result on QEMU 8.2.2. It is not a pass.

What was not run
----------------

the 30-round icount suites were not re-run for this baseline. Task
creation and a successful compile are not boot success. The 128M
